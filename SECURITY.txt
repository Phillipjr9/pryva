PRYVA SECURITY
==============

No system is unhackable. This is a concise description of controls and known
limits, not a penetration test or a guarantee. See OPERATIONS.txt for practical
setup, backup, recovery, email and financial incident procedures.

1. The threat model
-------------------

Protect customer identity, sessions, wallets, payout instructions, service
credentials and support conversations against credential stuffing, stolen
sessions, spoofed webhooks, duplicate payment or delivery requests, unsafe
provider responses, malicious input and accidental cross-environment access.
Operators and their sessions are high-value targets. A compromised provider key
or production database can bypass protections that exist only in application
code. Do not treat an unverified account or an attacker-controlled email address
as proof of identity.

2. What is implemented, and where
---------------------------------

- src/lib/identity/account-lockout.ts and the shared rate limiter bound sign-in attempts;
  neither alone stops a distributed attack.
- src/lib/identity/admin-two-factor.ts and admin authorization separate operators from
  customers. Verified operator addresses and 2FA are required by default.
  src/lib/identity/two-factor.ts stores TOTP secrets encrypted under TWO_FACTOR_KEY
  (AES-256-GCM, scrypt-derived) and refuses sign-in rather than skipping the second
  factor when that key is missing. REQUIRE_2FA_FOR_ALL extends the rule to every
  customer; it is off unless set to "true", and while it is on the only reachable
  routes for an unenrolled account are its settings page, the enrolment endpoints,
  sign-out and whoami.
- src/lib/platform/turnstile.ts challenges public signup with Cloudflare Turnstile,
  and the signup route refuses a filled honeypot before it writes an account. The
  challenge is enforced only when NEXT_PUBLIC_TURNSTILE_SITE_KEY and
  TURNSTILE_SECRET_KEY are both set; /admin/security reports which state the
  deployment is in, including the case where the secret is set but the *build*
  shipped without the site key (NEXT_PUBLIC_* is inlined at build time, so that
  deployment renders no widget and needs a redeploy, not a variable). Once
  configured it fails closed: a refused token is a 400 and a Cloudflare outage is
  a 503, never an unchecked signup.
- Account creation with Google meets the same challenge. The callback
  (src/app/api/auth/google/callback/route.ts) verifies a Turnstile token before it
  inserts a user, and the token is bound in a short-lived cookie by
  `/api/auth/google` because Google's redirect returns only `code` and `state`.
  Returning customers are never asked. The return leg is also limited per
  connection (20 per 15 minutes) before any Google call is made.
- src/lib/email/signup-alert.ts notifies operators when an address is confirmed, or
  on a Google signup, and only on the first verification. Signup itself is silent,
  so an unverified bot no longer generates mail to the operator inbox. Creating a
  verification link is separately capped per account (5 per hour), because each one
  is a real outbound message.
- Expensive authenticated reads carry their own budgets
  (src/lib/platform/rate-limit.ts): search, the order list and the bank directory
  are per-account; search runs leading-wildcard `ILIKE` scans, and the bank
  directory is the only authenticated read that calls the payment provider, so its
  upstream fetch is also collapsed into one in-flight request per instance.
  Refusals are 429 with `Retry-After`, and a counter that cannot be read is a 503,
  never an allowance.
- src/lib/platform/security-headers.ts and src/proxy.ts apply browser security headers;
  the CSP has deliberate limitations noted below.
- src/lib/payments/paystack-webhook.ts and webhook routes verify signatures; settlement,
  refund and ledger paths use transaction and idempotency guards.
- src/lib/payments/daily-reconciliation.ts checks wallet history; a missing or failed
  reconciliation is not a clean run.
- The wallet-email outbox snapshots attempted payloads, limits retries with
  provider idempotency, exposes failures for review and does not copy sensitive
  support messages into notices. eSIM and number delivery emails intentionally
  contain service secrets and must be treated as sensitive.
- Account closure removes credentials, sessions and delivery snapshots while
  retaining financial records. Requests already handed to a provider cannot be
  recalled. src/lib/identity/retention.ts describes the separately gated retention sweep.
- scripts/backup-db.mjs and scripts/restore-db.mjs provide a second logical
  backup/restore path; provider backups and recovery drills remain essential.

3. What this pass changed
-------------------------

Actual human support replies, passkey changes and eligible later purchases now
have event-triggered notifications and dedicated illustrations. Account closure
clears email-change requests and delivery snapshots. Email-change confirmation
and direct security notices distinguish a provider acceptance ID from an
unconfirmed response. These controls do not verify production delivery.

4. Known gaps
-------------

- There is no independent penetration test, comprehensive security review or
  bug bounty. Do not interpret tests as proof against attackers.
- Edge bot defence and a WAF are outside this repository; distributed abuse can
  exceed per-IP controls. Review firewall and account-lockout telemetry.
- The signup challenge is off until both Turnstile keys are set. Until then the
  honeypot, the 10-per-hour-per-IP signup limit and the 20-per-15-minute Google
  return limit are the only signup filters, and a determined script defeats them.
  Setting only the site key is worse than setting neither: the widget renders and
  nothing checks its token. Setting both but never rebuilding is the same trap for
  a different reason — the page has no widget — which is why /admin/security
  reports the build state separately from the variable state.
- Per-IP limits are only as good as the client address. On Vercel the edge
  overwrites X-Forwarded-For, which is what `clientIp()` reads; on a host that
  appends instead of overwriting, a caller can choose the address it is counted
  against. Verify this with the host before relying on the per-IP ceilings.
- CAPTCHA raises the cost of an account; it does not verify a person. Signup risk
  scoring (src/lib/admin/fraud.ts) remains advisory and queues suspicious accounts
  for review rather than blocking them.
- The CSP permits unsafe-inline in places; replacing it requires a nonce-based
  design and testing, not simply removing a directive.
- SPF, DKIM and DMARC depend on the sending domain's DNS and provider settings;
  verify them with the owner before making any change.
- ADMIN_2FA_REQUIRED=false weakens operator access and should not be left set.
  Plan recovery before changing TWO_FACTOR_KEY.
- Verify preview database and secret isolation in the host. Skipping preview
  migrations alone does not prevent runtime access to production data.
- Direct 2FA, email-address-change, reset-link and gift-card emails include
  best-effort paths. They are not covered by the outbox retry guarantee.
- A single operator may approve sensitive operations; maker-checker approval
  and out-of-band identity recovery require operational processes.
- Dependencies and credentials change over time. Run the production dependency
  audit, rotate leaked credentials, and verify provider configuration.

5. The operator checklist
-------------------------

Use verified, limited operator accounts and 2FA. Protect and rotate secrets;
never put credentials into the repository or logs. Isolate preview and live
databases. Back up and rehearse restoration to a separate database. Configure
and monitor cron, reconciliation, provider webhooks and delivery failures.
Verify real provider results with a user-controlled account and mailbox before
relying on a launch. Get authorization before production promotion or DNS work.

6. Reporting a vulnerability
----------------------------

Contact https://pryvalogs.com/contact with enough detail to reproduce the issue.
Do not test against a live account that is not yours, run automated scanners
against the site, extract another customer's data, or send passwords, security
codes or payment details in a report. /.well-known/security.txt is the public
contact record; review its expiry date before it expires.
