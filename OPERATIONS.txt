PRYVA OPERATIONS
================

Keep this operational guidance separate from customer-facing copy. Tests use
mocks and embedded PostgreSQL; they are not evidence that providers, hosting,
email delivery, account recovery or payment settlement work in production.
Have the owner authorize production promotion and infrastructure changes.

1. Environments and deployment
------------------------------

Keep production database credentials and provider keys out of preview and
local environments. Verify the host's actual environment-variable scopes; a
preview build that skips migrations can still read or write a production database
if production credentials are present at runtime. A preview without persistent
database credentials uses empty in-memory data, and is not an integration test.
Purchase, payment, refund and cron paths have preview guards, but a preview is
not globally read-only: other authenticated routes can still access or change a
shared database. Isolate both the database and provider credentials regardless.

Set NEXT_PUBLIC_SITE_URL to https://pryvalogs.com in production. Check the
approved Google callback in the Google Console matches the app callback at
https://pryvalogs.com/api/auth/google/callback. Inspect the legacy
NEXT_PUBLIC_APP_URL and the WEBAUTHN_ORIGIN and WEBAUTHN_RP_ID settings as well;
stale overrides can still select a retired host. Check the Paystack return URL
and any provider-side allowlists. These external settings have not been verified.
Do not change DNS, registrar, Vercel domain settings or other infrastructure
without owner authorization.

Back up before migrations. npm run db:migrate applies all top-level numbered SQL
files in order and stops on failure. Production builds apply migrations before
building, while previews do not. Migrations therefore need to be compatible with
the old live application as well as the new application. Apply all outstanding
migrations, including 0032, 0033 and 0034 where applicable. Migration 0034
preserves pre-existing closed-account snapshots, email-change requests and
passkeys; the current worker skips their queued email. Those historical records
may still contain sensitive data and need a separately authorized privacy review.
An earlier version of 0034 was applied by the production deployment on 5 November
2026, and included deletes of those closed-account rows. The build log confirms
application but does not report affected counts. Editing the file neither restores
records nor causes the filename-based ledger to re-run it. Any investigation or
restoration must be separately authorized; do not restore data blindly.

Older workers lack the new skip rule and can claim or update historical jobs; some
older versions may not check for closure before sending. Coordinate the scheduler
with the owner during a mixed-version rollout. The migration rejects late passkey
or email-change inserts for closed owners, including from an old app instance. During mixed-version rollout, an old passkey removal concurrent with
closure can deadlock; PostgreSQL aborts one transaction, which should be retried
after checking its result. Verify the backup and schema before allowing traffic.
Never manually replay historical migrations or the legacy directory against an
incompatible database.

2. Signing in as an operator
----------------------------

The operator console is a separate surface; operators do not get the customer
storefront. /admin/login and /login are both sign-in doors. A verified account
listed in ADMIN_EMAILS goes to /admin; customers go to /dashboard. Admin access
requires email verification and, when ADMIN_2FA_REQUIRED is enabled (the
default), two-factor enrolment. /admin/account is the operator's 2FA setup path.
Preview bootstrap is preview-only and is not a production access method.

Set ADMIN_EMAILS after the account exists and is verified:
  1. Leave the address out of ADMIN_EMAILS and sign up normally.
  2. Confirm the address from the verification email.
  3. Add the verified address to ADMIN_EMAILS using the host's secret manager.
  4. Follow the owner's deployment approval process, sign in, and enrol 2FA at
     /admin/account before depending on the account for operations.

Requiring a second factor from every customer is a separate, off-by-default rule
(REQUIRE_2FA_FOR_ALL=true). Unlike the operator rule it is a wall in front of the
store: an unenrolled customer cannot browse, buy or open their wallet. Only their
settings page, the enrolment endpoints, sign-out and whoami stay reachable, which
is what lets them satisfy it. Before switching it on, confirm TWO_FACTOR_KEY is
set and stored somewhere reachable without this deployment; losing it refuses
every enrolled account at sign-in with a 503. To let people back in during a
recovery, set REQUIRE_2FA_FOR_ALL to "false" -- that reopens the storefront
without touching any stored secret.

Adding the allowlisted address before signup can block the account from being
created. Do not permanently disable ADMIN_2FA_REQUIRED to work around setup.
Plan recovery before rotating TWO_FACTOR_KEY: changing it without a migration
makes enrolled authenticator secrets unreadable. If all enrolled accounts fail,
restore the prior key rather than mass-clearing factors. A customer who loses an
authenticator should use a single-use recovery code; if none remain, verify their
identity independently before any operator-assisted reset. A support message from
a possibly stolen session alone is not identity proof. Never paste a key into
logs, Git, tickets, a screenshot or chat.

Google sign-in does not automatically link an existing account merely because
the provider returns the same email. Google-only legacy users without a bound
subject require verified, operator-assisted recovery; do not bulk-link identities
by email. Passkeys are bound to their relying-party domain, so changing domains or
WEBAUTHN_ORIGIN can make existing credentials unusable. Plan a recovery path.

3. Email and delivery
---------------------

Configure a verified RESEND_FROM_EMAIL, RESEND_API_KEY, RESEND_WEBHOOK_SECRET
and CRON_SECRET on the production deployment. Verify the sender and credentials
in the provider, perform a genuine send to a mailbox the operator controls, and
verify the webhook separately. Provider acceptance is not proof of inbox
delivery. Check bounces, complaints and webhook delivery in Resend and the
operator integration diagnostics. SPF, DKIM and DMARC are operator-managed;
request approval before changing DNS. Rotate any credentials exposed in chat.

The repository schedules /api/cron/nightly at 01:20 UTC. Timely retries also
require an authenticated scheduler calling GET /api/cron/wallet-emails at least
once per minute with Authorization: Bearer <CRON_SECRET>. POST is supported.
This frequent scheduler is not installed by the repository; daily cron alone is
not sufficient. Alert on a non-200 result, scheduler failure, old pending jobs or
review jobs. Each call processes a bounded batch and the app shares a rate
budget; add capacity and coordinate all senders if volume exceeds it.

The durable outbox queues ledger movements, withdrawal states, bank links,
password changes, eligible purchase milestones/receipts, marketplace delivery,
number codes, eSIM delivery, human support replies and passkey changes. It
snapshots the recipient and the exact first attempted payload. A retry reuses the
same Resend idempotency key and body. An ambiguous request older than 23 hours,
an idempotency conflict, test-labelled legacy messages and invalid payloads go
to review; do not automatically reset or replay them. Changing Resend accounts
or keys can invalidate provider deduplication assumptions. Test Paystack keys
hold financial notifications for review rather than presenting them as live.
Security and support notifications remain eligible.

Only actual human support replies trigger a support email, without copying the
conversation or assistant trace. A passkey alert contains no credential or
device label. A receipt does not promise delivery; gift-card codes do not appear
in purchase receipts. The separate eSIM and number-delivery messages intentionally
contain the purchased service's activation details or code: treat their stored
payloads and mailbox as sensitive. Email-change confirmation, email-change
security and 2FA notices are currently best effort rather than durable; password
reset and gift-card delivery also have best-effort paths. Monitor provider logs
and investigate reports rather than promising a retry where none exists.

When an account closes, its saved outbox snapshots and email-change requests are
removed with its identity, without erasing financial history. An email already in
flight to the provider cannot be recalled. After commit, the app makes at most one
best-effort closure-confirmation attempt to the previously verified address. The
address exists briefly in process memory and at the email provider, not in an app
retry queue; a lost callback or failed send is not retried. No closure email is
sent to an unverified address or from the in-memory preview database. Monitor mail
errors without logging addresses. Old clients that cannot submit the exact balance
acknowledgement must refresh before forfeiting a positive balance.

The owner chose a ten-year retention horizon after account closure (31 Oct 2026).
It is an internal policy, not a number to add to customer-facing promises. The
nightly destructive purge is disabled unless RETENTION_PURGE_ENABLED=true. When
armed it works in bounded batches and holds accounts with unfinished payouts; the
read-only retention diagnostics can show what is due without purging it. Review
legal obligations, backups and outstanding disputes before enabling any purge.

4. Payment and fulfilment safety
--------------------------------

A wallet credit is valid only after the verified top-up and ledger credit commit.
A debit receipt is not proof of fulfilment. A withdrawal request or processing
notice is not proof of bank payout; a completed notice is not a bank statement.
The ledger, provider status and authenticated operator queue are the records to
reconcile. Never reset a processing payout, retry a transfer, issue a refund or
change a status just because a response or webhook was missing: an earlier action
may have succeeded. First investigate provider references and ledger history.
Use the existing idempotency and review paths, with operator authorization.

Production rejects Paystack and gateway test or unrecognised keys. Use live keys only
with an authorized launch plan. Switching keys does not erase earlier test-funded
wallet credits or reverse transactions. Whether previous tests shared the current
live database is unknown, and historical top-ups do not reliably identify test
versus live. Before allowing live withdrawals, an authorized operator must
reconcile Paystack's test and live records against wallet and bank-transfer history,
including downstream spending, refunds and payouts. Preserve evidence; do not
automatically delete, reset or adjust customer records. Escalate uncertain cases
for review rather than inferring that a balance is safe from a key change.

A configured eSIM catalogue is not a guarantee of stock. Unverified sample plans
are not shown; preview environments must not make live catalogue, purchase or
completion calls. Keep provider and sourcing details out of customer copy. Check
service availability and costs with an isolated account before taking real money.

The nightly job runs reconciliation and bounded sweeps, including number codes,
refunds, eSIMs, scheduled orders, payouts and onboarding. Check its status and
reconciliation_runs; a missing run is not a clean run. The destructive retention
sweep remains off unless explicitly enabled. Investigate alerts rather than
assuming the job repaired every uncertain transaction.

Referral-credit and purchase safety rollout (not yet production-verified):
* Schedule a controlled, quiet rollout: stop financial mutations and workers,
  take and verify a backup, apply migrations 0036 through 0040 in order, deploy
  the matching application, then validate with an isolated environment before
  reopening traffic. Old application instances must not run financial writes
  while provenance is being established. Do not run these steps on production
  without the owner's approval and a tested rollback/recovery plan.
* Referral rewards are spendable but cannot be withdrawn. Migration 0038 marks
  historical referrers and connected gift recipients as unknown; it preserves
  their total balances but blocks withdrawals until an authorized, audited
  source-of-funds review. There is currently no operator reconciliation tool to
  release these holds. Do not simply set wallet_provenance_known=true or assign
  zero restricted credit: reconstruct ledger, gifts, refunds and prior payouts,
  preserve evidence, have a second authorized reviewer verify the calculation,
  and use a separately designed, tested and audited adjustment workflow. Until
  that exists, these customers may be unable to withdraw legitimate cash.
* Historical bulk debits were not associated with individual orders. Automatic,
  self-service and admin order refunds now require a matching per-order debit;
  legacy bulk refunds may require an authorized reconciliation and separate
  audited adjustment workflow. Do not bypass the check or assume a missing debit
  proves the customer was not charged.
* Bulk checkout reserves the batch and a linked debit per unit before supplier
  calls. An interrupted batch is not resumed automatically: processing/review
  units and batches require provider and ledger reconciliation. Unattempted units
  are refunded during a completed request; a crash can leave them reserved for
  review. Apply migration 0040 before deploying bulk checkout.
* The SMM panel has no idempotency key. Boost checkout now retains uncertain
  outcomes for review instead of automatically refunding or retrying. Inspect
  historical failed/refunded boosts against supplier records before any action.
  A review or processing boost blocks new boosts until an operator reconciles it.
* Any pending or review order, claimed schedule, or processing payout may have
  reached its provider, even if its reference or response is missing. Do not
  retry, refund, resume or mark it settled based only on missing local data.
  Reconcile provider records and wallet ledger first. Legacy processing payouts
  are no longer eligible for manual retry or rejection by this endpoint.
* Refund sweeps rotate unconfirmed candidates but still require a definitive
  provider check and a matching debit; inspect logs and backlog, and verify actual
  scheduler frequency and duration. There is no guarantee of a five-minute refund.

5. Backups and incident response
--------------------------------

Enable and test the database provider's backups/PITR. The application archive is
an additional logical snapshot, not continuous recovery. On an authorized host:

  npm run db:backup
  npm run db:verify-backup -- path/to/archive.ndjson.gz

Backups contain customer data. Encrypt them, restrict access, keep an independent
copy and never commit them. Restore drills belong in a separate empty database:
apply migrations there first, verify the archive, then use npm run db:restore
with the documented --file, --target and --confirm-restore arguments. Never
restore over production or use --allow-overwrite without explicit approval and a
recovery plan. Verify row counts, financial invariants and access before routing
traffic to a restored database. These scripts need an appropriate connection;
check scripts/backup-db.mjs and scripts/restore-db.mjs before use.

Signed in but every page says signed out? Check /api/auth/whoami before changing
anything. If it reports cookie.duplicateSessionCookies true, the browser is
holding two pryva_session cookies -- a host-only one from before the domain move
and a Domain=pryvalogs.com one written after it -- and the stale copy is being
read instead of the live one. That is not a browser cookie problem and signing in
again will not clear it, because each sign-in adds another cookie rather than
replacing the old one. The app now tries every copy the browser sends and expires
the dead ones on sign-out, so signing out and back in once resolves it. Clearing
this site's cookies also works.

For suspected compromise: contain access, rotate affected secrets through the
host/provider, invalidate sessions as appropriate, preserve evidence, reconcile
payments and contact the owner. Avoid logging credentials, full bank numbers,
recipient addresses, customer messages or activation codes. ALERT_WEBHOOK_URL
can surface application errors, but logs and alerts are not a substitute for
provider monitoring. See SECURITY.txt for known gaps and safe reporting.

Unattempted bulk reservations
-----------------------------
A verified administrator can POST an orderId and a reason (10–200 characters)
to /api/admin/bulk-unattempted using the authenticated same-origin JSON admin
session. The endpoint refunds only a processing bulk unit whose durable marker
still says the provider was not contacted, with one exact linked debit. Its claim,
wallet credit and administrator audit entry commit together. It cannot settle a
unit whose provider call started or whose outcome is ambiguous; check supplier
records and use the separate confirmed-reconciliation process for those. Once
all units are terminal, replaying the original batch closes it without spending.

Telegram Stars (FoxReload): the new path is disabled by default and is not a
blanket enablement of other FoxReload products. Before enabling, apply migration
0041, configure FOXRELOAD_API_KEY and confirm a usable reference exchange rate
(or set a verified FOXRELOAD_USD_NGN_RATE; digital retail markup is 40%), verify the current account-specific
product and contract with the supplier, and verify a mock or otherwise approved
test. Then explicitly set FOXRELOAD_STARS_ENABLED=true. Do not put supplier keys
in client code. Preview and ephemeral databases refuse purchases. The supplier
must be funded for live fulfillment. Provider create/pay timeouts or unexpected
responses are held for reconciliation, not automatically retried or refunded.
Review the reconciliation queue and provider evidence before taking action;
never treat a missing response as proof of no supplier spend. An interrupted
processing claim may need manual investigation and has no automatic rollback.
The nightly job checks a bounded, rotating set of Stars orders; the order page
also offers a status check. Unconsumed expired quotes are pruned by the nightly
job; consumed quotes are retained as order evidence.

FOXRELOAD DIGITAL CODE CHECKOUT — LOCAL ONLY / NOT READY TO ENABLE
The digital-code slice is disabled by default with FOXRELOAD_CODES_ENABLED=false.
It supports exactly one verified non-financial, no-note code per order, from an
explicit operator-reviewed FOXRELOAD_CODE_OFFERS JSON array. Each entry must be
{id, name, region, countryCode, marketRegion}, where id is the exact FoxReload product ID, name is the exact
English product name returned to the configured account, and region describes its
actual redemption restriction. countryCode and marketRegion must match the exact
supplier attributes country_code and region, or be null when absent. A changed
attribute invalidates the quote before debit. Example shape only (not a real offer):
[{"id":"product_0123456789abcdefghijklmnop","name":"Example US game key","region":"United States","countryCode":"US","marketRegion":null}]
Do not copy the example as inventory. Before approving any actual SKU, verify
account access, currency, supplier price, stock, product type, redemption terms,
regional restrictions, consumer compliance, and how the exact data is delivered.
Never approve financial/card/crypto products here. The code path is not a banking
card program and does not implement card ownership or credentials. Empty or
malformed configuration allows no new products. Region and name changes
invalidate existing unused quotes.

Quotes use a 40% markup and expire in two minutes. If FOXRELOAD_USD_NGN_RATE
is set, it must be valid and is used as-is; it has no freshness alarm. If unset,
a validated USD/NGN reference rate no older than 36 hours is used, with no stale
or hard-coded fallback. A changed price or unavailable rate blocks checkout.
The reference rate is not proof of actual account funding or conversion costs.
Migration 0041 must be applied. Account-specific mock order/response behavior,
provider idempotency, every approved SKU and the release procedure still require
verification. A provider order is created and paid only after a wallet debit;
ambiguous outcomes remain in review, are never automatically retried/refunded,
and need supplier evidence. Interrupted processing requires audited operator
reconciliation. The nightly sweep only reads provider status and only marks an
order delivered for a consistent completed, non-mock single-code response.
Multiple pieces, missing data, unrecognized status and returned errors remain in
review; customers should not buy again while an outcome is unresolved. Codes are
bearer secrets: they are stored for the owner's order page, not sent in purchase
API responses. Do not put supplier data, API keys or codes in logs/tickets.

The eight legacy brand gift-card routes remain separate and are not repaired by
this slice. This work does not implement general direct/login top-ups, eSIM,
card issuance/top-ups or all catalogue SKUs. Later sections document subsequent
implementation and deployment. Obtain approval before live paid supplier orders.

FOXRELOAD DIRECT TOP-UPS — LOCAL ONLY / NOT READY TO ENABLE
The direct-top-up slice is disabled with FOXRELOAD_TOPUPS_ENABLED=false and has
an empty FOXRELOAD_TOPUP_OFFERS allowlist. It accepts only explicitly reviewed
product IDs with an exact supplier name, country_code/region attributes, display
region, specific restrictions in terms, min/max quantity and one to eight reviewed non-secret identifier fields.
The available field keys are username, login, account_id, user_id, userid, player_id,
playerid, game_id, gameid, server, server_id, zone, zone_id, uid, email, phone,
and phone_number. It refuses password, session, payment-card and unreviewed
fields and all banking products. Optional reviewed field types are string, email,
integer, number, and select (with exact approved choices); unspecified means
string for backward compatibility. A changed supplier type or choice blocks sale.
The separate FOXRELOAD_LOGIN_TOPUPS_ENABLED gate covers reviewed login_topup
products that require only these non-secret fields. It also requires
FOXRELOAD_CLIENT_CODES_ENABLED=true for possible confirmation challenges;
password and other credential fields remain unsupported.

FOXRELOAD_TOPUP_OFFERS is a JSON array. Shape example only, NOT a real SKU:
[{"id":"product_0123456789abcdefghijklmnop","name":"Example game top-up","region":"United States","terms":"Only for US accounts.","countryCode":"US","marketRegion":null,"min":1,"max":1,"fields":[{"key":"player_id","label":"Player ID"}]}]
Verify the actual account's offer, allowed region, precise unit/quantity meaning,
required recipient fields, validation/prechecks and delivery behavior before
adding an item. Unknown/malformed fields, price/currency/stock, region or bounds
fail closed. Never substitute fixed marketing prices for wholesale data.

A stable random FOXRELOAD_INTENT_SECRET of at least 32 characters (generate with
a cryptographically secure random generator) is mandatory. It protects the retry
binding and permits recipient verification without storing recipient data in the
order or browser recovery record. Do not rotate or remove it while any orders
are unresolved: old intents cannot then be checked or replayed automatically and
must be manually reconciled. The user must re-enter the same recipient details to
recover a lost response; losing browser storage, switching devices or re-entering
incorrect details limits recovery. Never log secrets or recipient details.

The supplier may return note/status formats different from the examples. A
mismatch on creation prevents payment; a mismatch while reading an order prevents
delivery confirmation. In both cases a wallet debit may need evidence-based
manual reconciliation. When the create response is lost, a read-only lookup by the original local
order ID can recover a uniquely matching supplier order after full verification.
Missing, ambiguous, mismatched or unpaid orders remain in review; no automatic
create/pay/refund retry is safe. New sales remain off until migration 0041,
account-authenticated product/contract verification, mock/live behavior and
operator reconciliation are verified. Recheck the USD/NGN funding rate; an
explicitly configured rate has no staleness alarm. No supplier funds or live orders have been touched.

For the direct-top-up slice, apply migration 0042 as well as 0041: it stores the
exact buyer-visible restrictions with each quote/order. Include detailed
country/account eligibility and exclusions in each offer's `terms`; a generic
"global" label is not sufficient evidence of universal redemption. Operator
review and account-specific verification remain mandatory before sales.

FoxReload eSIM rollout (disabled by default)
-------------------------------------------
FOXRELOAD_ESIMS_ENABLED defaults to false and FOXRELOAD_ESIM_OFFERS to empty.
Do not enable until supplier account access and exact eSIM fulfillment shape have
been verified, alongside a reviewed USD price/rate and product terms. Each JSON
allowlist entry needs exact id, name, region, terms, countryCode and marketRegion
(the latter two may be null). Include device requirements, coverage, data,
validity and activation constraints in buyer-visible terms. These are retained
with the quote; changed terms invalidate it. The checkout currently accepts
only a single LPA activation string in externalData plus a numeric ICCID in
externalId. This is an unverified assumption, not a promise about all supplier
products. Other formats, failures and uncertain payment results are held for
manual reconciliation. Never retry create/pay or refund merely because a call
timed out; verify upstream evidence and wallet state first. Disable new sales
without removing credentials if existing orders still need status checks.

FoxReload account confirmation codes (disabled by default)
---------------------------------------------------------
Migration 0043 adds a durable submission claim, not storage for the code.
FOXRELOAD_CLIENT_CODES_ENABLED defaults to false. When explicitly enabled, an
owner can check and submit a code only if a fresh matching non-mock supplier
order and item are both action_required and the recipient intent, currency,
quantity and price match. A single transactional claim moves the order to
processing before sending; a crash stays blocked for review. Explicit supplier
rejection permits a fresh code; a timeout, unexpected error or successful
submission blocks another attempt until reconciled. Never retry a submitted or
uncertain code, expose codes in logs, or refund without supplier evidence.
A future repeated challenge after acceptance needs manual review. No real
supplier account or code has been tested.

FoxReload read-only account check (local until deployed)
-------------------------------------------------------
The administrator-only /admin/foxreload screen can call the account and balance
GET endpoints using the key already stored on the server. It reports active state
and whether available USD/RUB funds are positive, zero or unknown; it never
shows the key, profile, amounts or raw supplier error. The check cannot create,
pay, cancel or refund an order. It also reports the sales gates, configured
reviewed-offer counts, rate/intent-secret presence and preview purchase guard.
A key set in Vercel is applied only to new deployments. Do not interpret this
check as evidence that any SKU can be fulfilled or that checkout is safe.
The separate legacy brand-gift-card checkout now requires
FOXRELOAD_LEGACY_GIFT_CARDS_ENABLED=true as well as the key and non-mock mode.
Leave it disabled: its matching, pricing and reconciliation still require review.
Existing requests can be replayed by request ID even while new sales are blocked.
The same administrator screen provides a read-only product search and contract
inspection. Search results are limited to 50; missing or unrecognized metadata
must not be inferred. This screen never changes an allowlist or creates an order.
The account probe also reports the number and recognized currencies of balance
rows without exposing values; unknown does not imply an empty wallet.

DIGITAL CATALOGUE STOCK VISIBILITY
The customer catalogue is a read-only discovery view, separate from account
funding and the reviewed checkout gates. It leads with a paginated catalogue
and requests listings with reported stock by default; customers can include all
listings with the stock filter. Stock status is a snapshot, not a guarantee of
account eligibility, region, price or the ability to order. The page never
exposes wholesale cost or supplier identifiers. Unreviewed or disabled listings
remain visible but do not gain checkout links, and quote/purchase paths retain
all of their existing checks. A supplier outage, missing key, rate limit or
financial-environment restriction may still prevent catalogue access.
