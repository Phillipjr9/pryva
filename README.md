# Pryva

Next.js application for a wallet and digital services. The repository supports an **in-memory preview** and a persistent deployment, but most live service purchasing is deliberately disabled until the provider integration, catalog mappings and payment/reconciliation workflows have been verified. What is live is deliberately narrow: Paystack wallet top-ups, manually settled withdrawals, virtual numbers and rentals for the ten plans in the fulfilment allowlist, account-marketplace checkout where its key is configured, gift cards, and the free disposable inbox. Everything else returns an actionable `503` rather than pretending.

Operating the deployment — secrets and rotation, migrations, scheduled jobs, money operations and incident playbooks — is documented in [`RUNBOOK.md`](RUNBOOK.md).

## Local development

```sh
npm ci
npm run dev
```

Open `http://localhost:3000` and use the demo login. Without `DATABASE_URL`, users, sessions, balances and orders are held in memory, shared only within one server process and lost on restart. **The one-click demo account is public and shared:** other visitors can view or change its activity. Never enter real personal information, passwords, payment details or other secrets in it. Preview funds and orders are simulated; they are not real money or services. The demo has its own simulated top-up and withdrawal flows with review, animated processing and downloadable demo receipts; real Paystack top-ups, transfers and the Paystack webhook are disabled in this mode. The demo wallet stores only the amount, method and request ID in this tab's session storage until confirmation, so an interrupted request can be retried without duplicating the demo transaction. Browser session storage is required to start these simulated wallet transactions. Support messages remain in the preview and do not reach support. Shared-profile name changes are local to the current view, and visitors cannot inspect or revoke one another's sessions. Do not use the preview database for a multi-instance or production deployment.

In the Arena in-memory preview, the gateway serves this sandbox's `PORT-SANDBOX_ID.e2b.app` host over HTTPS even when an internal proxy hop reports `X-Forwarded-Proto: http`. The app corrects the protocol only for that exact sandbox's preview hosts and uses secure partitioned session cookies for embedded previews. If the gateway drops request cookies, one-click demo login uses an opt-in service worker to keep the **public shared demo session** in the browser's CacheStorage and forward it in a same-origin header. This token is accessible to scripts on that preview origin, so never enter secrets in the shared demo. The bridge accepts only existing demo sessions, only in the current in-memory sandbox; it cannot authenticate private accounts or a persistent deployment. Email and Google sign-in still require working cookies and may not work when the gateway strips them. Other hosts and persistent deployments must provide correct trusted proxy headers; these preview exceptions do not relax the same-origin check.

Run the checks with:

```sh
npm test
npm run typecheck
npm run lint
npm run build
```

The same commands run on every pull request and push to `main` in
[`.github/workflows/ci.yml`](.github/workflows/ci.yml), together with
`npm run pricing:audit -- --check`, which fails when a generated price has drifted
outside the 30–50% band. They need no secrets: providers are mocked and PostgreSQL
runs in-process.

Security tests include embedded PostgreSQL/WASM SQL and transaction checks plus mocked providers and authentication. They do not replace tests against a separate PostgreSQL server, multiple application instances, or live payment/supplier sandboxes.

### Dashboard service hub

The dashboard's **All services** hub asks for a country or territory before showing categories and supports search and service-type filters. The ISO location directory is not a claim of supplier coverage (country names: `country-list`, MIT; flag artwork: `flag-icons`, MIT). In the in-memory demo, verification, social promotions, bundles, data and subscriptions have fictional prices and stock. Each selected service explains its own demo package and delivery; eSIM activation codes, proxy credentials, phone numbers and inboxes are fictional and cannot be used. Demo purchases atomically update the process-local wallet, orders and simulated inventory; owned counts show unused demo units for the corresponding demo catalog. Number and inbox orders begin without a code, then an authenticated owner-only poll creates one fictional code after seven seconds. Bundles expose their remaining units on the order and can simulate another code without another charge. An active number rental keeps the same fictional number and rental unit while simulating subsequent codes. Promotions complete as a fictional campaign. Subscription links preserve the selected country as browsing context, not verified coverage; subscription demo stock and owned units are shared across countries. The optional `country` in `POST /api/demo/digital` must be a valid country code and is part of the idempotent selection: retry the same request ID with the same plan and country. Country pools, prices, codes and account samples are inventions, not evidence of supplier availability or platform support. Bulk and manually run scheduled demo orders are listed separately and are not counted against the country-hub pools.

Fleexa is the selected supplier for its supported verification, email OTP and rental services. With a server-side key in persistent mode, the hub **attempts a read-only catalog** alongside the clearly marked examples. SMS and rental entries appear only when their supplier-provided country explicitly matches the selection; temporary email listings are not country-specific. Counts and marked-up prices are indicative, unknown values remain unknown, and the hub does not expose supplier identifiers, wholesale costs or the key. Responses can be partial or unavailable: Fleexa's detailed contracts have not been verified here, and listings without explicit country metadata are deliberately omitted. The list is not proof that a particular service can be ordered, and customer-owned units are not tracked there yet. **All Fleexa purchases and cancellations remain disabled** until country/app mapping, pricing, paid fulfillment, stock and reconciliation are verified in staging. Do not assume Fleexa supplies promotions, eSIMs, airtime or other categories. The demo never contacts Fleexa. The live account marketplace may separately show its supplier's validated stock when configured, with a manual refresh and last-checked time. Its listings lack reliable country metadata, so they are not filtered by the selected country; stock can change before checkout. The demo marketplace instead supplies fictional samples with no usable credentials.

Gift cards are explained at `/gift-cards`. The page quotes `src/lib/gift-card-rules.ts` — the same constants `createGiftCard` validates against — so the advertised range (₦1,000–₦500,000) and validity (12 months) cannot drift from what the API accepts. A card is bought from the buyer's wallet, redeemed once for its whole amount by a different account, and is non-refundable; the recipient email is a record, not a delivery address, and the buyer sends the code themselves.

Gift-card balance checks use an authenticated same-origin `POST /api/gift-cards/check` with a JSON body `{ "code": "..." }`; the old GET endpoint returns 405 so bearer codes are not sent in URLs. Update any external consumers and avoid recording codes in access logs, analytics, screenshots or support messages.

### Navigation, search and self-service destinations

Every published page is reachable from the footer, and `src/app/sitemap.ts` lists the help centre, customer-feedback page and each blog post. `robots.txt` disallows `/dashboard`, `/admin` and `/api`. Catalog "Get started" buttons link to `/signup?plan=<slug>`; both auth pages resolve that slug through `src/lib/plan-destination.ts` and send the visitor to the matching plan (the demo item in preview, the live plan page otherwise) instead of the generic dashboard. An unresolvable slug falls back to `/dashboard` rather than to an invented link. The catalog pages render no header of their own — the shared site header already reflects sign-in state.

An order id that is not the visitor's renders the 404 page rather than silently bouncing to the order list. The service hub still falls back to its country picker for an unrecognisable `country` or `category`, but it now names the rejected values so the reset is visible.

The dashboard command palette (⌘K / Ctrl+K, and an icon button below `lg`) searches the visitor's own orders, wallet transactions and gift cards through `GET /api/search` and links each result to its page. Wallet transaction history offers CSV/JSON export via `GET /api/wallet/transactions/export`, and **Settings → Your data** downloads the account archive from `GET /api/user/export`. Self-service deletion stays unavailable on purpose (`DELETE /api/user/delete` returns 503 until settlement and record retention are designed), so the panel points at support instead of offering a control that always fails.

Support messages submitted from `/contact` or `/dashboard/support` are read and triaged at **`/admin/messages`** (filter, search, and status changes through `PATCH /api/admin/messages`). The public contact page renders the same shared form as the dashboard, so one topic vocabulary reaches that inbox. The admin overview's fourth statistic is the real open-message count; it previously displayed a hard-coded "+12%" growth figure.

Privileged actions that move money or change an account — manual refunds, withdrawal approval, rejection and settlement, hand-prepared deliveries, administrator wallet adjustments and support-message status changes — write an entry to an append-only audit log at **`/admin/audit`** (API: `GET /api/admin/audit`). Each entry snapshots the acting administrator's email, the action, its target and a redacted summary; credentials, verification codes, full bank account numbers and support message bodies are never copied into it. The write is **best-effort by design**: it happens after the money has already moved, so a failed insert is logged loudly and does not turn a committed refund into a retryable failure. The wallet ledger remains the authoritative financial record — treat the audit log as the who-did-it record beside it, not as a complete one. What still needs a person is on **`/admin/reconciliation`**: withdrawals in flight, orders whose supplier outcome is unknown, refunded orders whose upstream unit may still be live, and deposits that have been pending for more than an hour. It is read-only, never shows a bank account number, and is ordered oldest first.

The in-memory preview database evaluates drizzle conditions itself. It now supports `like`/`ilike`/`not ilike`, `in (...)` value lists, and `or(...)` grouping nested inside `and(...)`. Previously an `or` collapsed to its first comparison, an `inArray` list was dropped entirely (matching every row), and `ilike` compared against the literal `%term%`, so preview text search returned nothing while appearing to work.

## Deployment configuration and prerequisites

The following are server-side environment variables unless otherwise noted. Store secrets in the deployment environment, not in the repository.

- `DATABASE_URL`: PostgreSQL connection string. Back up existing data and apply the ordered migrations in [`migrations/README.md`](migrations/README.md) before deploying.
- `ADMIN_EMAILS`: comma-separated, explicitly authorized email addresses. There is **no default administrator**; the demo identity can never be an admin. The allowlist is a privilege boundary, not proof of identity. See provisioning below before setting it on an existing deployment.
- `PAYSTACK_SECRET_KEY`: server-only Paystack secret used to initialize checkout and verify webhook signatures. Configure it through the hosting provider's secret settings; never put it in client code, URLs, source control, or chat. Use separate test and live credentials.
- `NEXT_PUBLIC_APP_URL`: the external HTTPS **origin** used for the Paystack return URL, e.g. `https://app.example.com` (no path, query, fragment or credentials). Public return URLs must use HTTPS; only local development permits HTTP localhost. `NEXT_PUBLIC_SITE_URL` can also pin the external origin for OAuth behind a proxy.
- `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`: optional Google sign-in credentials. Configure the provider's callback URL for `/api/auth/google/callback`. Google accounts must have a verified email and are bound by their Google subject, not email alone. Existing unlinked accounts need secure recovery; see the migration guide.
- `TWO_FACTOR_KEY`: server-only passphrase, at least 16 characters, that encrypts every stored TOTP secret. Without it two-factor authentication is **unavailable rather than optional**: enrolment is refused, and an account that already has it enabled is refused at sign-in with HTTP 503 and no session — never silently let in on the password alone. Rotating the value makes existing enrolments unreadable, so plan the recovery in [`RUNBOOK.md`](RUNBOOK.md) before you change it.
- `BULKACC_API_KEY`: optional server-only key for the primary account-marketplace catalog and orders. **Setting this key on a persistent database turns live purchasing on for that path** — there is no second switch to forget, so set it only once the account is funded and the reconciliation process is understood. `BULKACC_API_URL` optionally overrides the API base for staging. The key travels as a query parameter, so request URLs are never logged. Top the account up first: an order is refused when the balance is short, and the refusal is reported as such rather than as a delivery failure.
- `ACCSZONE_API_KEY`: optional credential for the legacy account-marketplace catalog, kept as a **fallback** for when the primary source is out of stock or unconfigured. A key alone does not enable checkout on this path.
- `MARKETPLACE_LIVE_PURCHASES`: defaults off and now gates **only** the legacy `ACCSZONE_API_KEY` path. Setting it to `true` in a persistent database enables purchasing there; **do not enable it** until that source's behavior and the reconciliation process are verified in staging.
- `WARRANTY_DEFAULT_DAYS`: optional replacement-window fallback for account listings whose product group has no explicit value (default 30 days; streaming 120, video 60). Hand-prepared products carry their own per-product value in `data/manual-catalog.json`, which takes precedence.
- `USD_NGN_RATE`: optional manual pin for the USD→NGN rate used to price USD-denominated catalog items; it wins while set. `USD_NGN_FALLBACK` (default 1600) is the floor used when the hourly public-rate lookup fails. Without a pin the rate is fetched at most once an hour and cached, so listing pages never block on it.
- `FLEEXA_API_KEY`: optional server-only Fleexa key for the read-only supplier listings and legacy order checks. A key does **not** enable purchasing. `FLEEXA_BASE_URL` (or legacy `FLEEXA_API_URL`) is optional and accepts only `https://fleexa.com.ng/developer`; redirects are refused so the key cannot be forwarded elsewhere. Use a separate dedicated staging key; never use a live key in the public demo.
- `RESEND_API_KEY`: server-only Resend API key for wallet transaction mail. Create and configure it in the host's secret manager; never expose it to the browser, source control, logs or chat.
- `RESEND_FROM_EMAIL`: a sender on a domain verified with Resend, e.g. `Pryva <wallet@your-verified-domain.example>`. Configure real DNS and a verified sender before enabling delivery.
- `WALLET_EMAIL_TEST_MODE`: optionally set to `true` in a separate staging database to label all wallet emails as test activity. A `sk_test_` Paystack key also labels messages test mode. Never switch test-funded balances to a live environment.
- `CRON_SECRET`: a strong secret required as `Authorization: Bearer <secret>` for cron endpoints, including wallet-email retries. Live scheduled fulfillment and live automatic refund sweeps remain disabled.

The reverse proxy must overwrite untrusted `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Forwarded-For`, `X-Real-IP`, and `CF-Connecting-IP` headers and expose the site over HTTPS. The application uses the first forwarded client IP for throttling, so letting a client supply or prepend that value defeats IP limits. If the edge does not provide a valid IP, requests share an `unknown` bucket, so one visitor can temporarily exhaust the IP allowance for everyone behind that bucket; verify your proxy configuration before deployment. Admin and financial browser mutations check the request origin; requests without an `Origin` header may be accepted for non-browser clients.

Reviews are verified purchases. `/reviews` shows published reviews only, and `/admin/reviews` is the moderation queue. A review can be written only by the account that bought the order, only after it was delivered or completed, and only once per order (a unique index enforces it). Nothing is published without an operator decision, both decisions write an audit entry, and the public page deliberately carries no customer identity — not a name, not an initial. There is no seed or imported content: an empty page says it is empty.

The app is installable: `src/app/manifest.ts` serves the web manifest, `public/icons/` carries the 192/512 and maskable icons, and `public/sw.js` registers in production only. The service worker caches two things — the offline page and content-hashed build assets — and deliberately never caches HTML navigations or `/api`, because it outlives the tab and is shared by every profile on the device. It does not queue purchases: moving money requires the network.

Every response carries a Content-Security-Policy: scripts, styles, fonts and images are limited to this origin plus the two Google Fonts hosts and the Pexels image host, forms may only post here, the app may only be framed by itself (except the embedded preview), and plugins cannot load. `script-src` still allows inline code because Next.js, the home page's JSON-LD and the stale-bundle guard all emit it; a nonce-based policy is a known follow-up. Adding a new external asset host means editing `src/lib/security-headers.ts` — a test compares the policy with the font links and `next.config.ts` so the two cannot drift.

Two-factor authentication is TOTP (RFC 6238) with a ±1 step window. Each accepted time-step is recorded, so a six-digit code cannot be replayed inside its own 30-second window, including the code used to confirm enrolment. Sign-in issues a short-lived single-use challenge instead of a session; only its SHA-256 is stored, it expires after five minutes, it dies after five wrong codes, and it shares the login rate-limit bucket. Ten hashed recovery codes are issued once, each spendable exactly once. Disabling requires the password **and** a current code, so a stolen session alone cannot remove the second factor. Recovery-code use is not rate-limited beyond that shared bucket; monitor support reports of lost authenticators.

Authentication, selected purchase routes, gift-card checks/redemptions, contact messages, and security reports use shared PostgreSQL fixed-window rate limits; they fail closed with HTTP 503 if the rate-limit table or database is unavailable. Apply `0002_shared_rate_limits.sql` to every persistent deployment before routing traffic. Keys are stored as SHA-256 digests, not raw IPs or email addresses; low-entropy values may still be guessable. Expired rows are cleaned opportunistically after a one-day retention period; monitor table size and schedule `DELETE FROM rate_limit_buckets WHERE reset_at < now() - interval '1 day'` if traffic or database maintenance requires it. Preview counters remain process-local and are not suitable for production. The limiter is not a substitute for edge-level DDoS, account-takeover, or bot protections.

### Administrator provisioning

Admin access is granted by the authenticated user's email matching `ADMIN_EMAILS`. Public password signup now refuses configured admin and demo addresses, but older accounts may have been created without email verification. **Before enabling an address on an existing installation**, use a maintenance window to verify the account's ownership out of band, review/reset any untrusted password credential, and revoke existing sessions for that account. Otherwise an attacker who previously registered that email or retained a session could become an administrator as soon as it is allowlisted. Configure the allowlist before reopening public signup. A verified Google sign-in may create a new account for a configured address; no default password or demo admin is provided. Review access periodically.

This is not a complete authentication or security audit. Password accounts do not have a verified-email onboarding flow, and production deployment requires additional security review and operational controls.

### Wallet transaction email (Resend)

Apply migration `0005_wallet_email_outbox.sql` before taking wallet activity, then configure a verified `RESEND_FROM_EMAIL`, `RESEND_API_KEY` and `CRON_SECRET` in the deployment environment. PostgreSQL triggers atomically queue **new** wallet ledger movements, withdrawal processing/completed/rejected transitions, and saved marketplace purchase deliveries; there is no historical backfill. Top-ups are notified only after the verified wallet credit commits. A debit email confirms a wallet movement, not fulfillment; a separate marketplace completion email follows only when delivery is saved. A withdrawal request or processing email is not proof of a bank payout. Rejection and any wallet refund are separate events. The demo neither queues nor sends real mail.

After eligible requests the app starts a best-effort batch, but reliable retry **requires a separate frequent scheduler** calling `GET /api/cron/wallet-emails` with `Authorization: Bearer <CRON_SECRET>` (POST is also supported). Schedule at least once per minute and ensure the hosting function can run for 60 seconds; the endpoint processes up to four jobs per invocation and may need additional capacity or more invocations under sustained load. Vercel Pro's minutely cron or a frequent external scheduler can be used; a Vercel Hobby daily cron is insufficient for the 23-hour safety cutoff. This repository does not install a cron automatically. Set an alert when the scheduler fails or the endpoint returns a non-200 response. A shared PostgreSQL budget limits this application's Resend attempts to four per fixed second and reports `throttled` when work is deferred without starting an attempt. Resend's default limit is team-wide (10 requests/second), and other applications, databases and manual requests are not counted by this budget; monitor 429s, account quotas and queue age and coordinate all senders. Fixed-window boundaries and delayed network requests can still cause bursts.

The outbox snapshots the recipient and exact message, uses a stable Resend idempotency key and leases jobs between workers. `sent` means **Resend accepted the request**, not that the inbox received it; monitor bounces and delivery separately in Resend. Network timeouts and ambiguous responses are retried with the same key and payload. After 23 hours from the first attempt, unresolved jobs move to `review` rather than risk another send beyond Resend's 24-hour deduplication window; an idempotency conflict also requires review. Do not automatically reset or replay such jobs. Changing Resend accounts or API keys after an ambiguous send may defeat deduplication: investigate provider history before resending. Provider credentials, ledger descriptions, bank account numbers, gift-card codes, OTPs and balances are not included in these messages.

Monitor restricted logs and outbox state, including `pending`, expired `sending`, and `review` counts and age; the worker logs review/retry totals without recipients or email bodies. For example, run this with a restricted operator database role:

```sql
SELECT status, last_error, count(*), min(created_at) AS oldest
FROM wallet_email_outbox GROUP BY status, last_error ORDER BY status, last_error;
```

The outbox stores recipients and the exact mail payload, so restrict access and set a retention policy for completed messages consistent with financial and privacy obligations; retain unresolved jobs for manual review. Password signups do not yet verify email ownership, so verify addresses and review abuse/deliverability controls before using real funds. In a **separate staging database**, verify the sender and key, use test mode, run a test top-up, withdrawal and supported purchase, and check that committed events arrive only once, rollback produces no mail, withdrawal language is truthful, retries preserve the payload, and delivery/bounce monitoring works. Automated tests mock Resend and use embedded PostgreSQL; they do not prove live delivery.

### Fleexa catalog and legacy order checks

The historical read endpoints are attempted only with a configured key, and the authenticated catalog endpoint returns sanitized read-only listings. The parser accepts only recognizable list shapes, bounds responses, omits unknown country matches and does not expose raw provider records. Some endpoints or fields may differ from the historical adapter: validate actual catalog and stock responses in a dedicated staging account with Fleexa before treating the feed as operational. Prices are marked up and indicative; no quote or live purchase is created. Legacy OTP polling uses a 25-second browser interval and a per-order 20-second minimum; a rental stays active for subsequent messages. Paid and state-changing supplier calls are hard-disabled, including cancellation, until the contract and reconciliation workflow are verified. Legacy live-order refunds require manual provider reconciliation.

Fleexa documents a 60-request-per-minute-per-key limit. A shared PostgreSQL budget allows at most 25 requests per fixed minute per app database, leaving boundary headroom, and a short process-local cache coalesces catalog reads. A fixed-window limit can still burst at boundaries, network delays can bunch requests, and other applications, separate databases or manual tools using the same key are not counted. Use an isolated key, monitor supplier 429s, and coordinate any external callers; this is not a guarantee of compliance with a rolling-window limit. The demo refuses supplier network calls even if a key is accidentally set.

### Paystack wallet top-ups

Before routing top-ups or webhooks to this version, back up the database and confirm `payment_topups` exists. It is included in the fresh baseline; older compatible schemas that lack it may need `migrations/legacy/005_create_payment_topups.sql`. Follow the migration guide rather than applying legacy migrations to a fresh baseline.

Configure Paystack's test-mode webhook URL as `https://<your-staging-domain>/api/webhooks/payment`, and separately configure the production webhook URL when going live. It must be publicly reachable and receive `charge.success` events with the `x-paystack-signature` header. The server verifies the raw-body HMAC-SHA512 signature, currency, amount, metadata and a matching server-created pending top-up; the status change, wallet credit and ledger entry commit together. A repeated matching event cannot credit twice.

The live wallet reviews the amount before opening Paystack's hosted checkout. The customer chooses from the payment channels actually enabled there; Pryva does not collect card credentials or a payment PIN. In an embedded view the user must follow an explicit top-level checkout link, because Paystack may refuse to load inside an iframe. The initialization API accepts `{ "amount": <whole NGN> }` and explicitly rejects the old, ignored `method` field; external clients must remove that field. A redirect is not proof of payment: the return verifies the reference on the server, and only a committed wallet ledger entry produces a success receipt. Ongoing, pending, processing, queued, abandoned and unknown statuses remain unconfirmed; a failed verification or network error does not justify paying again. The verified amount must exactly match the original top-up; if provider-side surcharges or other settings change it, the credit is held for manual reconciliation rather than rounded or guessed.

For recovery, the browser keeps the amount and reference in local storage until the credit is verified, using a separate key for each reference. It does not store checkout URLs or payment credentials. Browser storage is required to start a checkout. An unconfirmed reference can be checked again or cleared only after reconciliation; clearing it does **not** cancel a Paystack checkout or stop an in-flight payment. Another device, cleared browser data, or an interrupted initialization may not have the saved reference, so customers should check their wallet history or contact support before making a separate payment.

**Staging checklist:** Use a **separate** persistent staging PostgreSQL database; never point test keys at production balances or later switch a test-funded database to live keys. Test-mode recipients and credits must not be promoted to live. With all migrations applied, configure the Paystack **test** secret and the staging HTTPS origin securely, deploy, and set the test webhook URL in Paystack. Complete a test-mode checkout using Paystack's official test instructions and enabled channels. Confirm that the callback and signed webhook both arrive, that either order of delivery creates exactly one matching ledger credit, that pending/failed/mismatched payments never show a success receipt, and that an interrupted return can be recovered by reference. Exercise admin-approved transfers and merchant-side confirmation using Paystack's test facilities, then reconcile their final status. The automated tests use mocked provider responses and embedded PostgreSQL; they are not a live Paystack or multi-server settlement test. See [Paystack's transaction documentation](https://paystack.com/docs/api/transaction/) and [webhook documentation](https://paystack.com/docs/payments/webhooks/).

**Reconcile existing payments before cutover.** Payments initiated by older versions have no pending record in `payment_topups`, so their webhook events will not be credited by this version. Compare Paystack transactions against the old ledger and resolve each discrepancy with a controlled, auditable, once-only process. Never blindly replay or re-credit historical events. Test with Paystack test keys and a real staging database before using live funds.

**Reversals and disputes require operations.** The webhook acknowledges but does not process refund, chargeback/dispute or transfer events. A later reversal does not automatically debit a previously credited wallet, and there is no automatic alert or dispute workflow. Monitor Paystack independently and reconcile these events through a controlled, audited procedure; do not use real funds until the required operational controls and security review are in place.

### Account marketplace sourcing and hand-prepared fulfilment

Account listings are read through one routing layer (`src/lib/marketplace-suppliers.ts`) that merges up to three
lanes into a single catalog. Every lane produces the same listing shape, and each listing carries an opaque routing
token (`p1:`, `p2:` or `p3:`) as its slug, so the purchase route always knows which lane to call and a purchase can
never silently switch source:

| Lane | Token | Enabled by | Delivery |
| --- | --- | --- | --- |
| Primary catalog + orders | `p1:` | `BULKACC_API_KEY` | Instant, automatic |
| Legacy catalog (fallback) | `p2:` | `ACCSZONE_API_KEY` (+ `MARKETPLACE_LIVE_PURCHASES=true` to purchase) | Instant, automatic |
| Hand-prepared products | `p3:` | rows in `data/manual-catalog.json` | Admin fulfilment queue |

Streaming is the reason the hand-prepared lane exists: the primary catalog's streaming coverage is limited to Spotify,
while Netflix and Disney+ items have no verified API at all. Those products are listed from `data/manual-catalog.json`
with a per-product `costUsd` (the selling price is derived from it by `src/lib/pricing.ts`, never typed in by hand) and
a per-product `warrantyDays`. The lane publishes no stock count, because nothing publishes one: `stock` stays `null`
and the storefront says the item is confirmed after payment rather than inventing a number. It is closed entirely in
the preview database, so the demo cannot offer products it cannot deliver.

**Operating the queue.** A hand-prepared order is written with `provider: "manual"` and status `processing`, and waits
at `/admin/fulfilment` (API: `GET`/`POST /api/admin/fulfilment`). The admin buys the item, then either:

- `deliver` with exactly as many credentials as the customer paid for — the count is parsed from the order's plan
  label, and a mismatch is rejected rather than partly filled. The order becomes `delivered`, the credentials are
  stored on it, and `expiresAt` is set from the product's warranty so the replacement window is visible to the
  customer. Credentials are never logged; only the order reference and the item count are.
- `unavailable` with a short reason — the order moves to `review`, which is **not** a refund. Money is returned only
  through the audited refund endpoint, which requires `reconciliationConfirmed: true` plus that reason.

Delivering twice is refused (409), and the queue only ever acts on `manual`, unrefunded orders.

**Customer-facing secrecy is a tested invariant.** No customer-facing surface may name a source or reveal that stock is
bought in — not in copy, not in an error message, not in a JSON field readable in devtools, and not in a committed data
file. `src/test/supplier-secrecy.test.ts` enforces this three ways: it scans marketing surfaces and catalog copy for
source names and for disclosure words (supplier, reseller, wholesale, vendor, upstream); it scans every `"use client"`
module, because those ship to the browser and a vendor literal there is a leak even if nothing renders it; and it
asserts the committed hand-prepared catalog contains no source name, no link and no disclosure word. Client components
receive neutral, server-computed capability flags (for example `refreshableCode`) instead of provider names, and
provider literals live in the server-only `src/lib/order-providers.ts`.

> **This repository is public.** Source names in the server-only adapters, the wholesale costs in
> `data/cost-sheet.json` and `data/manual-catalog.json`, and the sourcing notes in this README are readable by

### Withdrawals and provider limitations

A withdrawal reserves wallet funds and creates its ledger record in one transaction. The API requires a client-generated UUID `requestId` in the JSON body alongside `amount` and `bankAccountId`. Retrying the same key for the same customer and parameters returns the existing request; changing the amount or account with that key is rejected. Existing external clients must supply and retain a key for retries, and all deployments must apply `0003_withdrawal_idempotency.sql` and `0004_paystack_transfer_reference.sql` first. The browser stores only the request ID, amount and internal account ID in local storage to recover after reload; it does not store bank details there. New requests use separate recovery keys so simultaneous tabs cannot overwrite one another, and older single-key records are still recoverable. Distinct request IDs are distinct withdrawal intents, so review history or contact support before creating another one after an uncertain outcome. Bank resolution displays the account name but does not establish ownership or identity. The browser supplies the displayed `expectedAccountName` on save; if a fresh Paystack resolution differs, the account must be verified again. The review flow and downloadable receipt confirm submission of a request, not settlement. Admin approval claims a pending request and stores a unique lowercase Paystack reference before contacting Paystack; the original wallet reference and Paystack transfer code are separate. Existing requests predate this field and have a NULL provider reference: reconcile all pre-existing pending and in-flight requests with Paystack before approval, retry or refund, especially any manually reset to pending. Use their historical details; never blindly retry or infer a new reference. An ambiguous transfer failure remains `processing` rather than automatically refunding; even a successful initiation is not proof of settlement. Operators must inspect the Paystack dashboard and match reference, amount, recipient and final status before marking a transfer complete or resolving/refunding it manually. Completion requires an initiation code, an explicit reconciliation confirmation and a note, which is logged; maintain a durable external audit record as well. Requests without a saved initiation code cannot be completed in the UI because the transfer might still be in flight; handle them through a controlled reconciliation procedure. Do not retry or refund an uncertain transfer until its outcome is confirmed. Paystack may require merchant-side transfer authorization or OTP; this app does not implement the merchant OTP-finalization flow. Transfer webhooks are not currently used to settle withdrawals automatically.

Live virtual-number and rental purchases run for the ten plans in the fulfilment allowlist (`src/lib/fulfillment.ts`) whenever the number provider is configured, each refused before anything is bought unless it clears the margin floor; the free inbox is live the same way, and temporary email is no longer a product at all. Live eSIM, proxy, digital/data, airtime, bulk and scheduled purchases remain disabled. Bulk, manual scheduled runs, simulated payments and demo inventory use synchronous copy-on-write mutations within a single preview process so failures do not leave partial simulated records; this is not a substitute for PostgreSQL transactions or multi-instance testing. Demo schedules do not run automatically: use **Run demo now** to simulate a run. The separate cron endpoint can process due preview schedules if explicitly configured, but this is not necessary for the manual demo. Demo data checkout uses a fixed fictional destination; the legacy `/api/airtime/purchase` endpoint no longer accepts preview purchases or phone numbers. The historical Fleexa adapter remains in the codebase for investigation, but its endpoints and catalog mappings have not been verified, and some advertised plans previously mapped to different countries or quantities. Legacy live-order refunds require manual provider reconciliation. The automatic refund cron refuses persistent databases; in preview it only considers simulated, expired single-number orders with no code. Rentals, eSIMs and other issued goods are not automatically refunded. Preview funds cannot create or approve real withdrawals.

Account-marketplace checkout is governed by the source that is configured, and can never use preview funds: the in-memory demo refuses every supplier call even if a live key is set by accident. With `BULKACC_API_KEY` present on a persistent database, purchasing is live on that path; the legacy `ACCSZONE_API_KEY` path additionally needs `MARKETPLACE_LIVE_PURCHASES=true`. Each checkout atomically records its wallet debit, order and ledger entry and then sends **at most one** supplier request — the listing is re-read once, before the debit, and never again inside the purchase. A timeout, rejection or incomplete receipt is left for review rather than retried or automatically refunded, because the primary source offers no idempotency key and a blind retry could double-spend. An order whose outcome cannot be determined is persisted for reconciliation instead of being reported as failed. Check the admin orders page for `processing`/`review` and use its provider reference to reconcile with the supplier. Do not refund while a request is in flight. Refunds for `review` orders require an administrator to supply `reconciliationConfirmed: true` and a reason to the manual refund endpoint **only after** verifying the outcome. A crash may leave an order in `processing`; there is no automatic resolver. Engineering must investigate and, only after confirming no request is in flight and reconciling the supplier, handle it through a controlled, audited operational procedure. Do not blindly change status, retry the purchase, or credit the wallet. The database-commit and credential-storage failure paths also require support review.

Self-service account deletion is temporarily unavailable because deleting a user currently cascades to balances and financial records. Direct customers to support until settlement, retention and anonymization are implemented. Validate provider contracts, pricing, delivery, idempotency, transaction concurrency and recovery against a real staging database and provider sandbox before using real funds.
